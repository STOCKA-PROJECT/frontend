# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

This project uses **pnpm** (a `pnpm-lock.yaml` is committed).

- `pnpm install` — install dependencies (runs `nuxt prepare` via `postinstall`, which regenerates `.nuxt/` types and the ESLint config).
- `pnpm dev` — start the Nuxt dev server on `http://localhost:3000`.
- `pnpm build` — production build (server output in `.output/`).
- `pnpm generate` — static site generation.
- `pnpm preview` — preview the production build locally.

There is no separate `lint` or `test` script defined. ESLint is wired via `@nuxt/eslint` and reads its config from `eslint.config.mjs`, which extends the auto-generated `.nuxt/eslint.config.mjs` — so `pnpm install` (or `nuxt prepare`) must have run at least once before `npx eslint .` will work.

## Architecture

Nuxt 4 application using the **`app/` source directory** layout (Nuxt 4 default — pages, components, composables, stores, etc. live under `app/`, not at the project root). The repository is currently a near-empty starter: `app/app.vue` only renders `<NuxtWelcome />`, and the only other source-level files are the root config files. When adding features, follow Nuxt 4 conventions inside `app/` (`app/pages/`, `app/components/`, `app/composables/`, `app/stores/`, `app/layouts/`, etc.).

Modules registered in `nuxt.config.ts` (these define the available toolset — prefer their idiomatic patterns over hand-rolled equivalents):

- **`@nuxtjs/i18n`** — internationalization. Locale files / config go through this module; do not introduce a separate i18n library.
- **`@nuxtjs/tailwindcss`** — Tailwind is the styling system. Use utility classes; avoid adding a parallel CSS framework.
- **`@pinia/nuxt`** — state management. Stores belong in `app/stores/` and are auto-imported.
- **`@nuxt/eslint`** — ESLint integration. The flat config is generated by Nuxt at `.nuxt/eslint.config.mjs` and extended by the root `eslint.config.mjs`; add custom rules inside the `withNuxt(...)` call rather than replacing the base config.

`tsconfig.json` is a solution-style file that only references the four tsconfigs Nuxt generates under `.nuxt/` (app, server, shared, node) — do not hand-edit those, regenerate via `nuxt prepare`.

`compatibilityDate` in `nuxt.config.ts` is pinned to `2025-07-15`; bump it deliberately when adopting newer Nitro/Nuxt runtime behavior.

## Context

This is the `frontend/` package of a larger `Stocka` project (parent directory contains other packages). Treat this directory as the root of the Nuxt app — backend code lives elsewhere in the monorepo.

## Skills — invoke before related work

Available skills are listed in the system reminder each session. Match the task to the skill **before** writing code, not after. Invoke via the `Skill` tool.

### Mandatory for this project

These cover the project's stack and must be loaded before touching the relevant code:

- **`vue-best-practices`** — MUST be loaded for any `.vue` file, Composition API, `<script setup>`, Vue Router, Pinia, or Vite-with-Vue work. Covers the four required references (reactivity, sfc, component-data-flow, composables) plus optional features (slots, fallthrough attrs, Teleport, Suspense, Transition, etc.).
- **`nuxt`** — for any Nuxt-specific work: `nuxt.config.ts`, `app/` directory conventions, server routes, `useFetch`/`useAsyncData`, middleware, layouts, auto-imports, hybrid rendering, deployment.
- **`vue-pinia-best-practices`** — when adding or modifying anything under `app/stores/`.
- **`vue-router-best-practices`** — when adding pages, navigation guards, route params, or route-component lifecycle interactions.
- **`vue-testing-best-practices`** — when adding/modifying tests (Vitest, Vue Test Utils, Playwright).
- **`vue-debug-guides`** — when diagnosing Vue runtime errors, warnings, async failures, or SSR/hydration issues.
- **`create-adaptable-composable`** — when authoring a new composable that should accept `MaybeRef`/`MaybeRefOrGetter` inputs.

Do **not** load `vue-options-api-best-practices` or `vue-jsx-best-practices` — this project uses Composition API + `<script setup>` exclusively.

### Workflow rules

1. Before any non-trivial change, scan this list and invoke matching skills via `Skill`.
2. For Vue/Nuxt work, `vue-best-practices` and (when applicable) `nuxt` are blocking — load them first, read the must-read references they point to, then code.
3. Skills referenced by `/<name>` slash commands (`/review`, `/security-review`, `/init`, etc.) are user-triggered; don't invoke them autonomously unless asked.
4. If a skill seems likely to exist for a task you haven't seen listed, run `find-skills` rather than guessing.
